# Root Release Metadata Synchronization Design

**Status:** Authorized corrective work for the Git-backed Authorial Flow release.

**Baseline defect:** The committed root `MANIFEST.json` and `SHA256SUMS.txt` remain byte-identical to 1.2 and report `graph_version=1.2.0-dev1`, while the 1.3 ZIP builder correctly generates fresh metadata inside each ZIP.

**Preservation mode:** P0 for article, project, policy, owner-gold, semantic-gold, and promoted learning material. This change is release tooling only.

## Root cause

`build_release()` deliberately excludes root metadata from source members and generates correct replacements inside the output ZIP. The release CLI has no operation that writes those generated bytes back to the repository root. Version 1.2 finalized the two files in a dedicated commit; the 1.3 release workflow built and verified a temporary ZIP but omitted that manual copy step. Existing tests verify only ZIP-internal metadata, so the stale committed files passed every gate.

## Approaches considered

1. **Add an explicit root-metadata sync operation (chosen).** Reuse `build_release()` in a temporary directory, read its verified `MANIFEST.json` and `SHA256SUMS.txt`, and atomically install those exact bytes at the repository root. Expose this through `scripts/build_release.py --write-root-metadata` and add an executable regression.
2. **Delete committed root metadata.** This removes staleness but breaks the release-baseline reconciler's installed-tree contract and the existing one-command upgrade design.
3. **Continue manual ZIP extraction.** This preserves current architecture but repeats the exact human omission that caused the defect and cannot be regression-tested as a release command.

## Selected behavior

`write_root_release_metadata(repo_root)` will build one temporary release with the existing deterministic builder, extract only the generated root metadata entries, stage both destination files under same-directory temporary names, and atomically replace each destination. Temporary files are removed on failure. Root metadata remains excluded from its own member list, avoiding self-reference.

The recorded `source_commit_sha` is the commit containing every release member before the final metadata-only commit. The source-commit resolver will walk backward across commits whose changed paths are exclusively root `MANIFEST.json` and `SHA256SUMS.txt`, then report the first content-bearing commit. This matches the established 1.2 finalization pattern and makes a release rebuilt from the clean final metadata commit byte-identical to the root metadata.

The CLI accepts `--write-root-metadata` without requiring `--out`. Existing `--out` behavior remains unchanged. If neither operation is requested, argument parsing fails rather than silently doing nothing.

## Tests

1. Build a synthetic committed release tree containing deliberately stale root metadata.
2. Invoke the real `scripts/build_release.py --repo <tree> --write-root-metadata` command.
3. Assert the new root manifest reports the current graph version and exact synthetic content commit.
4. Assert every listed path's size, SHA-256, and executable flag matches the source tree; neither root metadata file lists itself.
5. Assert `SHA256SUMS.txt` is exactly the manifest's path/hash mapping.
6. Commit only the synchronized root metadata, rebuild the ZIP from that clean final commit, and assert the ZIP metadata remains byte-identical and still identifies the content commit.
7. Run the existing deterministic ZIP, baseline-reconciliation, complete-suite, clean-extraction, and protected-tree gates.

## Release finalization

After code, tests, and verification notes are committed, run the sync operation once and commit only `MANIFEST.json` plus `SHA256SUMS.txt`. Then rebuild the ZIP and prove its embedded metadata is byte-identical to the committed root metadata and its source commit equals the pre-metadata commit.
