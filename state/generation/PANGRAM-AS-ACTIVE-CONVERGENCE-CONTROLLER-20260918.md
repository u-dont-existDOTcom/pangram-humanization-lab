# Method lesson — Pangram worked when it became an active convergence controller

Date: 2026-09-18
Status: **ACTIVE HUMANIZATION METHOD LESSON / DIRECT CURRENT-TARGET EVIDENCE**

## Question

Why did earlier owner-supplied Pangram screenshots fail to solve the Inner Child subsection, while the later GUI loop converged to a 100% Human boundary?

## What did *not* make the difference

It was not simply:
- Chat versus Joel clicking Pangram;
- API versus GUI;
- more detector data;
- a new global style rule;
- more positive calibration;
- a fresh writer context.

Joel had already supplied useful Pangram localization earlier.

The difference was **control-loop placement**.

## Earlier workflow

Detector evidence was treated mostly as:

`generate -> inspect result -> theorize about method -> rewrite architecture -> wait for another owner checkpoint`

This repeatedly introduced:
- new strategy hypotheses;
- new admission gates;
- new fresh-writer packets;
- same-model style forecasts;
- delays between measurement and the next local repair.

The detector result informed analysis, but did not directly control the next edit.

## Successful workflow

After the owner corrected the stale gate, the loop became:

`repair only current red regions -> preservation check -> Pangram GUI immediately -> use exact result -> repair current red regions again`

Measured sequence:

- Candidate F: AI 0.5329530835 / Human 0.4670468867
- Candidate G: AI 0.4243027866 / Human 0.5756971836
- Candidate H: AI 0.0 / Human 1.0

The same natural boundary was kept stable.
The owner-authored middle remained fixed.
Only the failed model-written regions were changed.

This is exactly the kind of coarse-to-fine external-feedback convergence seen in successful Episode 007.

## Causal lesson

**Detector feedback must sometimes function as a controller, not merely as evidence for later theorizing.**

When the detector is known to provide useful localization on a difficult humanization target:
- minimize time between measurement and next edit;
- preserve stable context;
- change only the regions the latest evidence says are still failing;
- avoid inventing a new strategy unless measured progress stalls or regresses;
- do not insert an owner-review gate before every cheap/reversible detector measurement if the owner has already authorized the route and the result will immediately change edit scope.

## Important boundary

This does not make Pangram editorial authority.

Joel can still reject detector-Human prose.

The successful loop works because three planes stay separate:
1. **preservation** — did meaning/source authority survive?
2. **detector control signal** — where is model signal still showing?
3. **owner editorial authority** — is the resulting prose actually acceptable?

The detector controls iteration only inside those boundaries.

## When owner-supplied screenshots are enough

Owner screenshots are fully valid evidence.

The failure earlier was not that Joel supplied them manually.

The failure was that Chat did not keep the next operations tightly coupled to the measured red/green map.

If Joel supplies a screenshot and its exact candidate identity is known:
- freeze the result;
- localize the red regions;
- repair those regions;
- remeasure promptly when authorized.

Do not convert the screenshot into another long strategy detour unless the measured repair loop itself has stopped advancing.
